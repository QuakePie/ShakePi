# ShakePie changes — 2026-09-15 (v1.1)

This document records what changed, why it changed, how it works, and how to modify it later.
The frozen `backup/version-1.0/` snapshot is untouched; all changes below are v1.1 work.

## 1. Root-cause fix: recordings were sampled at the wrong rate

### Symptom

The archive showed sample counts and times that disagreed with each other. A 15-minute
recording at the configured 200 Hz contained ~345,000 sample groups (≈383 Hz) instead of
~180,000, the live page reported a different rate than the hardware was producing, and any
spectrogram frequency axis computed from the nominal rate was scaled wrong by ≈1.9×.

### Root cause

Measured from a deployed recording (`SHAKEPIE_20260915T181500Z.spb`): the median gap between
consecutive sample groups was 2.632 ms → **379.9 Hz actual**, while every block header, the
recorder configuration, and the web catalog said **200 Hz nominal**. The ADS1256 hardware
source (`pi/src/ads1256.cpp`) free-runs: it records one group per DRDY event and never enforces
the configured cadence. The DRDY pipeline at `data_rate_sps=2000` delivers groups faster than
the requested 200 Hz, so the recorder stored everything while labelling it 200 Hz. The fake ADC
(`fake_adc.cpp`) always paced itself to the nominal rate — which is why the software tests never
caught the mismatch. The database was internally consistent (catalog matched file footers
exactly); the *data itself* was mislabeled, so every derived display was wrong.

### Fix

- New `PacedSampleSource` (`pi/include/shakepie/paced_source.hpp`, `pi/src/paced_source.cpp`):
  a portable `ISampleSource` decorator that paces `read_group()` to `1/nominal_group_rate_hz`
  on `CLOCK_MONOTONIC_RAW`, keeping the periodic grid, resynchronizing after stalls instead of
  bursting, and never sleeping on the first group. `recorder_main.cpp` wraps the hardware
  ADS1256 source with it. The fake ADC keeps its own pacing (unchanged).
- `validate_config()` (`pi/src/config.cpp`) now rejects hardware configurations where
  `3 × nominal_group_rate_hz >= adc.data_rate_sps`, because each group consumes three
  conversions the paced schedule must be able to afford.
- Tests: `tests/cpp/paced_tests.cpp` covers pass-through mode, exact grid cadence, stall
  resynchronization, result passthrough, and the new validation rule. All C++ tests pass on
  the Pi (6/6 CTest).
- Web defense for **historical** files recorded at the free-running rate:
  `recording_plot.analyze_recording()` now measures the effective rate from the file
  (sample count over the recorded time span) and builds the spectrogram frequency axis with
  it, so old recordings display correct frequencies too. `nominal_rate_hz` is still reported.

### Effect after deployment

New recordings contain exactly `nominal_group_rate_hz` groups per second; sample counts,
durations, live rates, dayplot timelines, and disk-usage estimates all agree. Old recordings
remain on disk and render correctly through the measured-rate path.

## 2. Web interface changes (`archive-web` 0.3.0)

### Plot alignment and color legend (live + recorded pages)

- Waveform and spectrogram canvases now reserve identical margins; previously spectrograms
  reserved a 64 px right margin for an in-plot colorbar, so the two plot areas had different
  widths and their time axes could not be compared directly.
- The colorbar was removed from inside the plot area and replaced by a labeled Magma gradient
  in the page legend strip (−120 dBFS quiet → −20 dBFS loud), which does not affect plot
  geometry. Live and recorded pages share the same legend treatment.

### Calendar day picker

- `/api/days` returns every UTC day that holds finalized recordings with per-day counts
  (`Catalog.available_day_counts()`).
- A dependency-free calendar popover (CSP-safe, part of `app.js`) is available on the Archive,
  Dayplot, and Recorded pages via a calendar button next to the day field. Days with data are
  highlighted and selectable; empty days are visibly disabled; the current day is outlined.
  On Archive/Dayplot it navigates to `?date=…`; on Recorded it loads that day's recordings.

### Automatic daily plots and canonical naming

- The dayplot worker now checks hourly (`auto_check_seconds`, `dayplot.auto_generate_days`)
  for **finished, gap-free UTC days** that have no cached plot and queues them automatically
  (`Catalog.auto_queue_completed_dayplots()`). A completed day therefore always ends up with
  its daily plot without anyone opening the interface.
- Generated files use canonical names `STATION_YYYYMMDD_<channel>_dayplot.png` under
  `dayplots/<UTC-day>/` (`naming.py`). The worker migrates legacy fingerprint-named files on
  startup (`Catalog.migrate_dayplot_names()`) and deletes unreferenced leftovers
  (`Catalog.cleanup_orphan_dayplots()`), so filenames stay stable for website uploads.

### Recorder settings from the interface

- New `recorder_settings.py` mirrors the recorder's C++ validation rules, renders updated
  configuration text in place (comments preserved), performs atomic writes with timestamped
  backups, syncs the web view rates, and restarts services through a fixed
  `sudo -n systemctl restart …` rule for the `shakepie-web` account only.
- New routes `GET/POST /settings` (`app.py`) with CSRF, session auth, and audit-log entries
  (`recorder_settings_applied` / `recorder_settings_failed`).
- `config.py`: `target_sample_rate_hz` and `live.sample_rate_hz` are no longer pinned to a
  single constant (25–2000 Hz, default 200), and a `[recorder_admin]` section selects the
  enabled flag and configuration paths.

### Other improvements

- Live status shows the **source rate** separately when it differs from the displayed rate;
  recorded-data summary shows the effective rate.
- The archive table's "Samples" column is now labeled "Sample groups" (each group is one N/E/Z
  triplet).
- The archive password CLI now accepts 8-character passwords (with a warning) so the chosen
  interface password can be applied; Werkzeug scrypt hashing is unchanged.

## 2b. Web interface changes — second pass (learning from AnyShake and Raspberry Shake)

A deeper study of AnyShake Observer's views and Raspberry Shake's rsudp/DataView/Control
Center produced a second round of adapted functionality (all original code):

- **Automatic event detection (STA/LTA)** — the signature feature of both projects. A new
  `detector.py` runs a persistent loopback stream client inside the web process and feeds the
  vertical channel through a from-scratch short-term/long-term average trigger (constant
  memory, hysteresis via `off_seconds`, a cooldown between stored events, and window resets
  on recorder restarts or rate changes). Finished events are persisted in a new `events`
  table (catalog schema v2, migrated in place from v1) with start, end, peak amplitude, and
  trigger ratio. The **Events page** lists them with links to the covering recording; the
  Overview shows detector state and the last event. Configuration: `[detector]` section of
  `archive-web.conf` (threshold presets follow the classic guidance: 4.5 for noisy sites,
  3–4 for quiet vaults).
- **Host system metrics on the Overview** (Raspberry Shake "Control Center" style): CPU load
  averages, SoC temperature, memory used, and uptime, read best-effort from `/proc` and
  `/sys` with graceful "Unavailable" fallbacks on other platforms.
- **Latest daily plot panel** on the Overview (the webcam-style "always one stable image"
  pattern): links to the newest complete dayplot day.
- **Dayplot click-through** (DataView's click-on-helicorder interaction): clicking a plot
  line on the Dayplot page maps the click to a helicorder row and opens the Recorded page
  with `at=HH:MM:SS`, which selects and loads the recording covering that time. Mappings are
  deliberately coarse (one plot row).
- **Shareable URLs** (AnyShake History pattern): the Recorded page syncs the selected date
  and recording back into the URL (`?date=…&recording=…`) via `history.replaceState`, and a
  **Copy link** button copies the current view.
- **CSV export** (AnyShake export-router pattern): `GET /recordings/<id>/export` streams one
  validated recording as timestamped CSV (`timestamp_utc,north_counts,east_counts,
  vertical_counts`) with bounded memory (a worker thread parses blocks into a bounded queue)
  and a generated filename; original `.spb` downloads remain available unchanged.
- **Data continuity health** (Raspberry Shake's "health = data continuity, not uptime"): the
  Overview now shows **data coverage for the UTC day so far** (merged, overlap-free coverage
  from the catalog via `Catalog.day_coverage_ns`) and **age of the last archived sample**,
  alongside the host metrics.
- **Confirm dialog** on the recorder settings form (AnyShake's destructive-action pattern):
  applying settings asks for confirmation because it restarts the recorder.
- **Dark mode** (DataView style): the UI follows the system preference, the topbar toggle
  overrides it (persisted in `localStorage`), and plot canvases are theme-aware through CSS
  custom properties consumed by the canvas renderer.

## 2c. New component — `shakepie-terminal` SSH console

A new installable package in `terminal/` gives the recorder a full-screen **terminal console**
(the raspi-config/lazygit style of navigation): arrow keys move, Enter selects, Space toggles
days in batch lists (`a` select-all, `n` none), q/Esc goes back, Ctrl-C quits. Rendering uses
rich; the SSH/SFTP layer uses paramiko; both are pure-Python and cross-platform (Windows,
macOS, Linux). The hand-rolled menu widget keeps the dependency tree to just those two.

Features:

- **Status and health**: recorder health JSON, HDD usage, SoC temperature, uptime, and the
  active state of the recorder, web, and dayplot-worker services.
- **Recordings**: days are grouped from the recorder's own filenames (catalog-independent).
  Batch download with per-file progress bars, **skip-already-downloaded** idempotence (same
  name + size), optional sha256 verification, and a local free-space consideration before
  large batches. Deletion is day-based, requires typing `DELETE`, and only ever removes
  finalized `.spb` files — live `.partial` files are untouchable by design, so deleting while
  the recorder runs is safe.
- **Dayplots**: batch download (or delete) of the generated daily plots, preserving day
  subfolders — ready for website uploads.
- **Recorder settings**: the same validated editor as the web interface (rules mirror
  `pi/src/config.cpp`), with an on-Pi timestamped backup before writing and a recorder restart
  after a successful apply; changes render as a preview before confirmation.
- **Logs**: the last 60 journal lines of any of the three services.
- **Scripting mode**: `--action status | list-days | download-days --days …` runs the same
  operations without menus for cron/automation; the password can come from
  `SHAKEPIE_TERMINAL_PASSWORD` (never from command-line arguments, which leak into process
  lists).

Security choices follow current guidance: host keys use **trust-on-first-use** with the key
fingerprint shown and remembered in a tool-local known_hosts file (system known_hosts are
honoured first); passwords are prompted per session and never persisted; sudo commands are a
fixed set with a `sudo -S` password fallback when passwordless sudo is unavailable.

Verified live against the recorder: status, day listing (8 days), a full 44-file / 239 MiB day
download, and an idempotent re-run that skipped all 44 files.

## 3. Automation scripts

- `deploy/download-dayplots.bat` — double-click Windows download of all daily plots via `scp`.
- `deploy/download-dayplots.ps1` — PowerShell variant with the same behavior.
- `deploy/download-dayplots.sh` — Linux/macOS variant.
- All three default to `caspian@caspian:/mnt/shakepie-data/dayplots` and copy into a local
  `dayplots/` folder; they remove the `tmp/` scratch directory and report the image count.

## 4. Research summary (AnyShake, Raspberry Shake)

- AnyShake `observer`/`explorer` are **AGPL-3.0** (plus paid commercial), `plotter` is GPL-3.0 —
  no code was copied; only ideas were adapted (canonical plot products, per-service status,
  settings-as-forms). AnyShake `spectrogram-js` is MIT but unnecessary here because the
  existing canvas spectrogram already works.
- Raspberry Shake: StationView/DataView are proprietary; org repos (`rsudp` etc.) are GPL-3.0 —
  likewise ideas only. Validated conventions: UTC-only plots, `STATION_channel_date` naming
  patterns, "Save & Restart" settings flow with validation before apply, health = continuity of
  recorded data rather than uptime.

## 5. Deployment notes

- Recorder: build on the Pi (`cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
  -DSHAKEPIE_BUILD_PI=ON -DSHAKEPIE_BUILD_TESTS=ON && cmake --build build && ctest`), install
  to `/opt/shakepie/releases/<id>`, flip the `current` symlink, restart
  `seisberry-recorder.service`.
- Web: copy `archive-web/` to `/opt/shakepie/archive-web`, `pip install -e ".[dayplot,production]"`,
  install the polkit rule (`deploy/49-shakepie-web-restart.rules`) and the file permissions from
  the README section, install the updated
  `shakepie-archive-web.service` (shipped with `/etc/shakepie` writable), then restart
  `shakepie-archive-web.service` and `shakepie-dayplot-worker.service`.
- Set the interface password with `shakepie-archive-password` (scrypt hash goes into
  `/etc/shakepie/archive-web.env` as `SHAKEPIE_ARCHIVE_PASSWORD_HASH`).
- Post-deploy verification: recorder health shows the nominal rate, a fresh 15-minute file
  contains ≈ `rate × 900` groups, completed days gain canonical dayplots automatically, the
  calendar highlights data days, and the settings page validates and applies a change.
