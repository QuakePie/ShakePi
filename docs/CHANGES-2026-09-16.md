# ShakePie changes — 2026-09-16 (zero calibration)

## Startup auto-calibration (behavior per operator request)

Calibration is now a **one-time-per-start** operation, not a continuous one: at every
recorder start the engine automatically runs one calibration — after
`calibration.startup_delay_seconds` (default 30 s, letting the electronics settle) it
measures over `calibration.startup_window_seconds` (default **300 s** = 5 minutes; 3–5
minutes is the intended range) and keeps those offsets for the entire run. While the
startup measurement runs, the previously persisted offsets stay applied, so recorded data
is centered from the first sample. Manual requests (web/SSH) remain available anytime and
use the short 10 s window. Offsets are persisted only after a terminal outcome
(applied/cleared); the watcher distinguishes *consumption* (serial bump) from *completion*
(terminal outcome) — the serial alone was insufficient because the engine bumps it when
the measurement starts, not when it ends. New `calibration.*` keys: `auto_on_start`
(default true), `startup_delay_seconds` (0–3600, default 30),
`startup_window_seconds` (30–3600, default 300).

## Play recordings as sound (audification)

New endpoint `GET /recordings/<id>/audio?channel=north|east|vertical` turns a finalized
recording into a mono 16-bit WAV at 8 kHz: the data is decimated to give a ~40x speed-up
into the audible range, peak-normalized to 80% full scale (every recording plays at the
same loudness; phone speakers are never overdriven), with a 60 s cap for very long
recordings. The Recorded data page gains a "Play as sound" control — pick the component
and use the browser's audio player. Deterministic: the same file always produces the
same sound.

## Nightly summary notification (Beijing midnight)

Every night at 00:00 Beijing time (`[notify] daily_summary = true`,
`summary_hour = 0`), the Pi pushes a one-screen digest to Bark: events detected during
the just-finished Beijing day, events the operator removed as false, hours of data
recorded with coverage percent (overlap-free, from the catalog), disk percent with
days remaining, and the recorder state with temperature. The scheduler sleeps until
the next Beijing midnight (UTC+8 fixed offset, no DST) and the summary bypasses the
event rate limit.

## Bark push notifications for detected events

Events now reach the operator's phone instantly: when the detector finalizes an event, a
summary (UTC time, duration, peak amplitude, trigger ratio) is pushed to the **Bark** iOS
app (`api.day.app`). Delivery runs on a dedicated daemon thread with a bounded queue so a
slow network never stalls detection; a rate limit (default one message per 10 minutes,
`[notify] rate_limit_seconds`) suppresses trigger storms and reports the suppressed count
in the next delivered message. The Bark device key is a secret stored in
`/etc/shakepie/archive-web.env` as `SHAKEPIE_NOTIFY_BARK_KEY`; without the key the
notifier stays disabled. New `[notify]` config keys: `enabled`, `bark_server`,
`rate_limit_seconds`.

## Sensor zero-mean calibration (recorder + web + SSH console)

The geophone front end produces a DC offset, so raw counts were recorded around ~+18,000
instead of zero. New functionality lets the operator recenter the data on demand:

### How it works

- Triggering a calibration (web Settings page button, SSH console menu item, or
  `shakepie-terminal --action calibrate`) writes a one-line request file
  (`/var/lib/shakepie/calibrate.request`).
- The recorder's watcher thread consumes the request within a second and hands it to the
  acquisition engine, which measures each channel's mean over `calibration.window_seconds`
  (default 10 s). **Recording never stops** and keeps using the previously applied offsets
  during the window; the new offsets replace the old ones atomically when the window
  completes.
- Measured means beyond `calibration.max_offset_counts` (default 4,000,000) are rejected —
  this protects against calibrating during a disturbance. Offsets are subtracted with
  saturation at the 24-bit boundaries; saturated samples raise the existing clipping status
  flag.
- Applied offsets are persisted to `/var/lib/shakepie/zero_offsets.conf` and restored on
  recorder startup, so data stays centered across restarts without recalibrating.
- "Record raw (clear offsets)" writes a `clear` request that zeroes the offsets immediately.
- Completion handshake: the engine bumps `calibration_serial` in the health telemetry for
  every consumed request; the watcher waits for the serial to advance. This works uniformly
  for the instant clear path and the timed measurement path.

### Files and permissions

Both control files live under `/var/lib/shakepie` (systemd `StateDirectory`, mode 0770,
group `shakepie`): the recorder can read/remove requests and persist offsets despite its
`ProtectSystem=strict` hardening; the web account (`shakepie-web`, group `shakepie`) and the
SSH user can create requests. An earlier design wrote to `/etc/shakepie`, which the recorder's
hardening correctly made read-only — that path is abandoned. A request file that cannot be
removed is parked (logged once, ignored) instead of re-triggering calibration forever.

### Surfaces

- **Recorder health** (`/run/shakepie/health.json`): `zero_offset_north/east/vertical`,
  `calibration_phase` (idle/measuring/failed), `calibration_outcome`
  (none/applied/cleared/rejected/disabled), `calibration_progress` (0–100),
  `calibration_serial`.
- **Web interface** → Settings → "Sensor zero calibration": live status line (state,
  progress, applied offsets) with a 2 s poller, "Calibrate zero level" and
  "Record raw (clear offsets)" buttons (CSRF-protected, audited as
  `zero_calibration_requested`).
- **SSH console**: Status view shows the offsets; Settings menu has "Calibrate sensor zero"
  and "Record raw again" entries; scripted `--action calibrate` and `--action clear-zero`
  for automation. Writes try the group-writable path first and fall back to sudo.
- **Recorder config** (`calibration.*` in `recorder.conf`): `enabled`, `window_seconds`
  (1–120), `max_offset_counts` (1–8388607), `request_file`, `state_file`,
  `restore_on_start`. All optional with safe defaults; absent keys keep existing
  deployments working unchanged.

### Tests and verification

- New `tests/cpp/calibration_tests.cpp`: applied/rejected/cleared/restored/clamped/disabled
  paths through the real acquisition engine (7/7 CTest suites green on the Pi).
- Web suite: request-file writes for both modes, unknown-mode rejection, CSRF rejection
  (72 passed).
- Verified live on the recorder: offsets ~+18,100 → live stream means −4/+48/−66 counts;
  clear and calibrate cycles over both the web and the SSH console; offsets restored after a
  recorder restart (journal line `calibration: restored zero offsets ...`).

## 2026-09-17 — MiniSEED export, N-of-M trigger, CENC watch source, hodogram, H/V, kiosk

### New features (archive-web)

- **MiniSEED export** (`GET /recordings/<id>/miniseed?channel=all|north|east|vertical`):
  dependency-free miniSEED 2.4 writer (`miniseed.py`) — 512-byte records, INT32 counts
  (encoding 3, lossless), little-endian, channels EHN/EHE/EHZ, network `SP`. Sample-sequence
  gaps and clock steps split the export into new record series with truthful start times;
  sequence numbers run continuously across the volume. Button "Export MiniSEED" on the
  Recorded data page. Exports are capped at 4M sample groups (~5.5 h) per request.
- **N-of-M coincidence trigger** (`[detector] minimum_components = 1..3`, default 1 = legacy
  vertical-only): with 2 or 3, each component runs an independent STA/LTA (own hysteresis +
  cooldown) and an event is stored only while that many components trigger simultaneously,
  which removes single-channel bumps/spikes from the event list. New `CoincidenceDetector`
  in `detector.py`; detector snapshot now reports `minimum_components`. Set to 2 on caspian.
- **CENC watch source** (`watch.py`): China Earthquake Networks Center feed
  (`https://www.ceic.ac.cn/data/data.json`, no official API). Times are Beijing time and are
  converted to UTC; magnitude/depth accept numeric strings; unusable rows are skipped. Watch
  point "Catalog" choices are now usgs / isc / cenc / both / usgs_cenc / all
  (`[watch] cenc_base` overridable). **Bug fix found on the way:** the query window was read
  after stamping the "checking" status, so every check looked back only 30 minutes instead
  of "since the last check" (capped 24 h); the previous check time is now captured first.
- **Particle-motion hodogram** (`GET /recordings/<id>/hodogram?start=&seconds=&max_points=`):
  downsampled N/E scatter (≤20k points) + principal polarization azimuth and linearity from
  the 2x2 covariance eigen-decomposition (single-station back-azimuth hint). Drawn on canvas
  from the Recorded data page "Particle motion" button with start/length inputs.
- **H/V spectral ratio** (`GET /recordings/<id>/hv`): Nakamura H/V from overlap-free Welch
  averages of N/E/Z, rebinned into 48 log-spaced bands; peak reported within 0.2–20 Hz
  ("H/V ratio" button). Ratio denominator floored relative to the loudest bin (no overflow
  on near-silent vertical).
- **Kiosk mode** (`/kiosk`, nav link "Kiosk"): chrome-less dark wall display — three live
  waveform lanes, UTC + Beijing clock, recorder state dot, rate / last-sample age /
  events-today / disk-remaining footer, fullscreen button (`kiosk.html`, `kiosk.js`,
  `kiosk.css`; CSP-safe, no inline script).

### H/V plot switch to log-log axes (2026-09-17)

`drawHvRatio` in `static/app.js` now draws the ratio axis logarithmically too
(the frequency axis was already log): 1-2-5 ticks per decade on both axes, the

## 2026-09-17 — CRITICAL FIX: all three channels were digitizing one input

### Symptom

The particle-motion hodogram always showed 45.0 deg azimuth with linearity 0.999, and the
H/V ratio was flat near 1.0. Raw-file analysis proved the cause: `east = north + 16` and
`vertical = north + 120` counts, sample for sample — all three channels carried the same
waveform with fixed offsets (exactly the differences of the stored zero offsets).

### Root cause (two stacked driver bugs in pi/src/ads1256.cpp)

1. **MUX never switched.** `read_conversion` issued WREG MUX, SYNC, WAKEUP, and RDATA
   inside a single chip-select frame while a conversion was pending; on the real chip the
   mux write did not take effect, so every conversion sampled AIN0-1 (the north pair).
2. **Settling conversion kept.** After restructuring into per-command chip-select frames
   (verified against the chip with the new `pi/tools/adc_probe.cpp` diagnostic), the first
   conversion after a channel switch was still settling and smeared each channel with the
   previous channel's tail — the frozen 45 deg azimuth persisted.

### Fix

`read_conversion` now follows the classic scan: wait DRDY -> read the settled conversion
for the current pair -> WREG MUX (own chip-select frame) -> SYNC -> WAKEUP -> wait DRDY ->
read and **discard** the settling conversion. Six conversion periods per group at most;
200 Hz groups need 1200 of the 2000 SPS budget. The static pacing guard moved from
`3 x group rate < adc.data_rate_sps` to `6 x` (config.cpp, web `recorder_settings.py`,
terminal `recorder_settings.py`, with updated tests). `Ads1256` unit tests now assert the
new byte pattern, including the discarded conversion.

### Data impact

**Every recording finalized before 2026-09-17 ~08:00 UTC is single-channel**: the N/E/Z
slots all hold the north geophone's signal (E and Z differ only by the stored zero
offsets). Hodograms, H/V ratios, and any polarization analysis on historical files are
meaningless. After the fix the true per-channel offsets measured completely different
values (north 18502, east -380, vertical 1059) and the 2.5 s polarization azimuth now
wanders (19-65 deg) instead of freezing at 45 deg.

### Diagnostic tool

`pi/tools/adc_probe.cpp` (build: `g++ -std=c++20 -DSHAKEPIE_GPIOD_V2 -I pi/include
-I protocol/include -o adc_probe pi/tools/adc_probe.cpp pi/src/ads1256.cpp
pi/src/linux_hardware.cpp -lgpiod`) reads back the MUX register and samples each input
pair with the recorder stopped; it prints a software-vs-hardware verdict.
