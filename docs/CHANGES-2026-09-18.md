# ShakePie changes — 2026-09-18 (dayplot naming + regenerate-all)

## New dayplot filename convention

Generated dayplots now use website-ready names

```text
<YYYYMMDD>-<STATION>-CH<n>.png     e.g. 20260914-Caspian-CH3.png
```

inside `dayplots/<UTC-day>/`. `CH1`/`CH2`/`CH3` are the north/east/vertical channels
(`naming.canonical_dayplot_name()`). `<STATION>` is the recorder's configured station ID
(`storage.station_id`) read from `/etc/shakepie/recorder.conf` through the new
`recorder_settings.read_station_id()` — i.e. the name follows the value edited on the web
settings page, falling back to the station recorded inside the files when the settings file
cannot be read. Unlike the previous convention the station keeps its configured case
(e.g. `Caspian` stays mixed-case). Renaming the station only affects newly generated files;
old images keep the name they were generated with.

The dayplot worker's startup migration now treats both legacy layouts as stale — the
fingerprint names (`<fingerprint>-<channel>.png`) **and** the previous canonical names
(`STATION_YYYYMMDD_<channel>_dayplot.png`) — and renames them to the new convention
(`naming.legacy_dayplot_name()` is the broadened detector). Unreferenced leftovers are
still removed. `deploy/download-dayplots.{bat,ps1,sh}` count and document `*.png` now.

## Regenerate-all-days button

The Dayplot page gains a "Regenerate all days" panel: `POST /dayplot/regenerate-all`
queues a **forced** dayplot job for every indexed day (`Catalog.queue_all_dayplots()`,
days with an active queued/running job keep theirs). The single-consumer worker then
regenerates the plots one by one, oldest day first — no web request blocks; progress is
visible per day as usual. The button asks for confirmation in the browser (the run can
take hours on a multi-month archive).
